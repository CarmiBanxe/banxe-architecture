### ADR-125 — Resolve triple IL-540 collision across PR #787/#788/#789 via sequential rebase-at-merge (gated, DO NOT MERGE)
- **Decision:** Created `docs/adr/ADR-125-triple-il-540-collision-resolution.md` (ACCEPTED, concept_only). Audit 2026-06-25 (HEAD `ec95496`, `origin/main` max IL-539, ADR max 122) found a **triple IL-540 collision**: PR #787 (ADR-123, permissions hardening — **primary**), #788 (ADR-123 operator apply-runbook), #789 (ADR-124, claude-code-setup eval) all branched from `main@ec95496` and each hardcoded `[IL-540]` (`max+1`). Same failure as the #744/#749/#751 precedent (IL-503/504/505). ADR number = **125** (next free; ADR-123/124 are reserved in-flight by #787/#789, not yet on main).
- **GATE (real stop-barrier, not best-decision):** resolution does NOT start until ADR-123 verify is **GREEN** — `skipDangerous` absent, push-deny for `main` present, push-allow without a bare `git push:*`. **GREEN as of 2026-06-25** (factory-verified read-only: all 3 conditions met in `~/.claude/settings.json`). The apply is an **operator out-of-repo step (ADR-103)** — the factory does NOT perform it and does NOT merge on its behalf, it only verifies the reported result.
- **Deterministic order (serialized, ADR-119 Rule 3, `strict` branch protection):** **A** — merge #787 → IL-540 frozen to ADR-123 (`main` max=540). **B** — rebase #788 onto new `main`, `python3 ledger/build_ledger.py` re-mints its shard to **IL-541** (strictly > main max), correct all human-facing `[IL-NNN]` → merge (max=541). **C** — rebase #789 onto new `main` → re-mint → merge. **D** — this ADR-125 PR merges **last**; at its own rebase-before-merge it re-mints to the next free IL. *(Planned integers 541/542/543 above; **actuals** after `#791`/`#792` interleaved are #787=540, #788=542, #789=544, this=**545** — see Status line.)*
- **Per-step verify contract (after every rebase, before merge):** `build_ledger.py --check` exit 0; no duplicate IL (values a unique set, new value strictly > prior main max); append-only preserved vs `git HEAD:ledger/IL-SEQUENCE.json` (added = exactly one new key, mutated=∅, removed=∅ — generator's `check_append_only`); CI `guardian-ledger` + `strict` protection green. A failed verify re-rebases (a duplicate is a rebase signal, NOT an operator question — ADR-119 Rule 8.5).
- **ADR-119 self-honoring (dogfood):** per Rule 8 the IL number MUST NOT be hardcoded at creation — it is `f(IL-SEQUENCE + base)`. On this branch's base (`ec95496`, max 539) `build_ledger.py` necessarily renders **this** shard as **IL-540** too — itself a 4th *provisional* claim, marked PROVISIONAL and frozen only at merge. Because this PR merges last (Step D), its rebase-before-merge re-mints it to **IL-545** (strictly > resolved main max **544** — `#791`/`#792` interleaved, shifting the plan). No PR title / commit / ADR `il_anchor` / companion doc asserts a **final** number belonging to another shard — they carry **IL-545**, the value the generator assigns on the resolved base.
- **Root cause:** no atomic IL allocation across concurrent worktrees cut from one base — N sessions off the same `main` all compute the identical `max+1`; numbering reconciles only at rebase-before-merge, which serializes *merges* but does not stop N branches *carrying* the same provisional number. Structural, not per-author.
- **Preventive follow-up (separate IL, NOT implemented here):** **atomic IL reservation at session start** — a lightweight lease (append-only `ledger/IL-RESERVATIONS.json` via atomic CAS, or short-lived `origin` ref `refs/il-locks/*`, or a `build_ledger.py reserve` subcommand) so a session obtains a unique prospective IL before writing its shard; converts merge-time reconciliation into start-time allocation, closing the carried-collision window. Scope/atomicity/CI to be specified in the follow-up.
