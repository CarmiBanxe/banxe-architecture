## 1. Executive Summary

The Phase 1 census flagged "AML Orchestrator" as a potential duplication across **vibe-coding** and **banxe-emi-stack**. This analysis confirms the two artifacts operate at **fundamentally different architectural layers** and serve entirely different purposes:

- **vibe-coding/src/compliance/aml_orchestrator.py** — a research-stage Python function aggregating algorithmic scoring signals
- **banxe-emi-stack/agents/compliance/swarm.yaml** — production AI agent topology with FCA-compliant HITL gates

**Finding:** NOT a conflict. No code consolidation required. Only S-1 sign-off required from MLRO and CTIO to formally attest that vibe-coding is research-only and banxe-emi-stack is production-authoritative.

## 3. Detailed Artifact Analysis

### 3.1 vibe-coding/src/compliance/aml_orchestrator.py

**Function signature:**
```python
async def assess(tx: Transaction, subject: Customer, wallet: Wallet) -> AMLResult
```

**Inputs:**
- `tx: Transaction` — payment transaction metadata (amount, currency, parties)
- `subject: Customer` — customer profile (name, jurisdiction, PEP status)
- `wallet: Wallet` — digital wallet context (if applicable for crypto flows)

**Processing flow:**

1. **tx_monitor signal** — call `score_transaction()` from `compliance.tx_monitor`
   - Evaluates velocity, amounts, patterns, time-of-day anomalies
   - Returns numerical score (0–100)

2. **sanctions_check signal** — call `screen_entity()` from `compliance.sanctions_check`
   - Matches customer name/IBAN against OFAC, EU consolidated list, UK consolidated list, UN consolidated list
   - Returns categorical: CLEAR, MATCH_REQUIRED_REVIEW, SANCTIONS_CONFIRMED, HARD_BLOCK_JURISDICTION

3. **crypto_aml signal** — call `analyse_chain()` from `compliance.crypto_aml`
   - Analyzes blockchain transaction history, mixer/coinjoin usage, exchange provenance
   - Returns categorical: CLEAN, SUSPICIOUS_CHAIN, CRYPTO_SANCTIONS

**Hard overrides (always REJECT):**
- `HARD_BLOCK_JURISDICTION` → REJECT (no appeal)
- `SANCTIONS_CONFIRMED` → REJECT (triggers SAR, no appeal)
- `CRYPTO_SANCTIONS` → REJECT (crypto-specific sanctions, no appeal)

**Decision thresholds (if no hard override):**
- Score < 40 → APPROVE
- Score 40–70 → HOLD (pending manual review)
- Score 70–85 → REJECT (block transaction)
- Score ≥ 85 → SAR (Suspicious Activity Report trigger)

**Output:**
```python
@dataclass(frozen=True)
class AMLResult:
    decision: Decision  # APPROVE | HOLD | REJECT | SAR
    score: int  # 0–100
    signals: dict  # { 'tx_monitor': score, 'sanctions': categorical, 'crypto': categorical }
    audit_payload: AuditRecord  # for logging
```

**Imports (all internal to vibe-coding):**
```python
from compliance.tx_monitor import score_transaction
from compliance.sanctions_check import screen_entity
from compliance.crypto_aml import analyse_chain
```

**No imports from banxe-emi-stack confirmed** (grep test below).

**Status:** Research prototype. Developed during the compliance architecture design phase to validate the signal aggregation model. Not wired into vibe-coding's production payment flow. No production deployment.

### 3.2 banxe-emi-stack/agents/compliance/swarm.yaml

**Configuration structure (YAML):**

```yaml
agents:
  mlro_agent:
    autonomy_level: L2  # alerts human, may act
    human_double: MLRO
    hitl_gates:
      - SAR_filing
      - AML_threshold_change
      - sanctions_reversal
      - PEP_onboarding
      - board_report_sign_off
    timeout: 4h
    
  jube_adapter_agent:
    autonomy_level: L3  # auto-processes, blocked at gates
    human_double: CTIO
    
  sanctions_check_agent:
    autonomy_level: L3
    human_double: MLRO
    block_threshold: 0.80  # ≥0.80 confidence → immediate block
    review_threshold: 0.60  # 0.60–0.80 → HITL review
    
  aml_check_agent:
    autonomy_level: L3
    human_double: ComplianceOfficer
    edd_thresholds:
      individual: £10000
      corporate: £50000
    
  tm_agent:
    autonomy_level: L3
    human_double: ComplianceOfficer
    alert_sla: 2s
    
  cdd_review_agent:
    autonomy_level: L2
    human_double: ComplianceOfficer
    
  fraud_detection_agent:
    autonomy_level: L3
    human_double: FraudAnalyst
```

**Orchestrator logic (`orchestrator.py`):**
- Loads `swarm.yaml` at startup
- Routes incoming transaction to appropriate agent based on customer profile and risk flags
- Enforces HITL gates: if autonomy_level says "HITL gate required", decision is blocked and escalated to `human_double`
- Logs all decisions to ClickHouse audit trail (I-24)
- Respects timeouts (e.g., MLRO gate: 4 hours before auto-escalate to CEO)

**Agent soul files** (`agents/compliance/soul/*.soul.md`):
- Each agent has a `.soul.md` file documenting its identity, capabilities, constraints, autonomy level, and audit logging
- Example: `tm_agent.soul.md` specifies "must alert MLRO on SAR candidate within 2 seconds"

**Status:** Production. Loaded at deployment. Active in EMI environment. Covers all FCA SYSC 6.3 requirements (AI governance) and EU AI Act Art.14 (human oversight).

### 3.3 Why They Cannot Be Merged

**Different artifact types:**
- **aml_orchestrator.py** is executable Python code — a stateless function that takes inputs and returns a decision.
- **swarm.yaml** is declarative configuration — defines agent topology, autonomy levels, HITL gates, and human double assignments.

These are **not the same thing**. Attempting to merge them would require:
1. Translating YAML agent declarations into Python function calls
2. Removing HITL gates (no place for them in a stateless function)
3. Removing human double assignments (function is autonomous)
4. Losing the agent soul files (context about each agent's constraints)
5. Creating a new coupling between the two repos (vibe-coding would import from banxe-emi-stack)

**Result:** Would be architecturally worse than the current state (two separate, uncoupled implementations).

**Correct relationship:**
- vibe-coding aml_orchestrator.py = **research reference** for the signal aggregation algorithm
- banxe-emi-stack swarm.yaml = **production implementation** of AI agent orchestration
- vibe-coding's research work informed the design of the EMI swarm, but the implementations are intentionally separate

## 5. Architectural Justification

Per **ADR-005 (Protocol DI Pattern)** and **compliance-boundaries.md**:

### Floor 2: AI Agent Orchestration
- Responsibility: Route transactions to agents, enforce HITL gates, manage human escalation
- Implementation: `banxe-emi-stack/agents/compliance/swarm.yaml`
- FCA scope: SYSC 6.3 (AI governance), EU AI Act Art.14 (human oversight)
- State: **PRODUCTION**

### Floor 3: Algorithmic Scoring
- Responsibility: Aggregate signals from multiple risk models into a single risk score
- Implementation: `vibe-coding/src/compliance/aml_orchestrator.py`
- FCA scope: MLR 2017 §45 (risk assessment methodology)
- State: **RESEARCH PROTOTYPE**

**Why separate:** Floor 2 (orchestration) and Floor 3 (scoring) are intentionally decoupled. The orchestrator does not need to know the details of how signals are aggregated; it only needs to invoke them and respect the results. The scoring function does not need to know about HITL gates; it only computes a risk metric.

**Why vibe-coding was designed first:** During the initial compliance architecture design (Phase 1), a research prototype was created to validate the signal aggregation approach. This proved successful. When EMI was launched, the production orchestration was built from the ground up with proper FCA AI governance, using the vibe-coding prototype as a reference for the algorithmic component (Floor 3), but implementing the governance layer (Floor 2) in EMI swarm.yaml.
