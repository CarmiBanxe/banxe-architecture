## Status

**PLAN only — no code, no tests, no ADR, no ledger shard in this step.** Next subtrack of the
**BANXE.RAR → EMI** earn vertical after M1.4 (advisory status taxonomy), **not greenfield**.
It is the **lowest-blast-radius** next step: a **read-only advisory analytics / summary**
layer that **aggregates the already-migrated advisory earn data** — `EarnMetrics`
(rates/fees/product, M1.2/M1.3) + `EarnAdvisoryStatus` (lifecycle taxonomy, M1.4) — into a
descriptive advisory summary, **on top of the existing** EMI `dse` / `dss_analytics_enrichment`
seam. No new legacy domain, no new external seam, no live data.

## Why this domain (mapping rationale)

Per `docs/migration/banxe_to_emi_mapping.md`, the **risk/DSE/analytics** slice is the P0
lowest-blast-radius lane and is already where the earn advisory work landed. M1.5 stays inside
it: it does **not** open a new legacy module — it **composes** the M1.2–M1.4 outputs into an
advisory analytics view. Adjacent un-started P1 slices (`crypto-api` wrap, wallets/accounts via
Midaz, KYC/AML wrap) and the P0 regulated payments rewrite are **higher blast radius** and
remain deferred.

## 1. Scope

**Legacy reference (source-of-truth for shape only, snapshot `banxe-crypto-earn`):** the
read-only analytics/summary DTOs noted in the M1.1 deep-read — `money-info`,
`position-balance`, `get-earn-fee`, positions summary — i.e. the **descriptive aggregation**
of an earn product's economics (yield + fee structure + lifecycle state). **Values stay mock**;
only the *summary shape* is traced.

**EMI target (reuse + small additive):** the existing analytics seam —
`src/banxe_trading_backend/services/dss_analytics_enrichment.py` + `dse/` (engine/models) —
surfacing a **read-only advisory earn summary** that composes:
- `EarnMetrics` (M1.2/M1.3): `current_yield_pct`, fee/product fields in `risk_summary`;
- `EarnAdvisoryStatus` (M1.4): lifecycle status vocabulary.

**Strategy = reuse + small additive** (compose existing advisory outputs); the exact summary
DTO/shape is decided in the M1.5 deep-read (step 0), not here. **Prefer keeping `EarnMetrics`
unchanged**; any new summary type is additive and advisory.

## 2. Numeric invariants (I-01)

- Any numeric in the summary (aggregated yield, total/effective fee, min amounts) MUST be
  `Decimal` / `DecimalString` via the existing `normalize_decimal` (M1.2/M1.3) — **no
  `BigNumber`, no `float` outward**, fail-closed on non-numeric. No parallel money type; no new
  rounding rule beyond the established 4dp DecimalStr.

## 3. Activation Safety

- **Advisory / mock layer ONLY** — a descriptive summary, **not** live balances, **not**
  execution. No invest/withdraw/payout, no payments, no fund movement.
- **No live data:** no real positions, balances, or APR — deterministic mock composition of
  already-migrated advisory values.
- **No prod wiring change, no feature-flag bypass, no network/keys, no crypto-wallet/crypto-api
  seam.** Default earn provider stays `"mock"`; fail-closed for non-wired/unsupported inputs.

## 4. Duplication Audit (ADR-102) — MANDATORY before any M1.5 code

Repo-wide Duplication Audit is **required** before touching code (no delete/merge without it):
1. Search for existing analytics / summary / enrichment / aggregation representations — esp.
   `services/dss_analytics_enrichment.py`, `dse/` (engine/models), any earn summary DTO.
2. Confirm **reuse** of `EarnMetrics` (M1.2/M1.3) + `EarnAdvisoryStatus` (M1.4) as the inputs —
   **do not duplicate** the rate/status sources (single source-of-truth preserved).
3. Identify the source-of-truth + every consumer of the analytics seam; no second analytics
   path.
4. Attach a "Duplication Audit" section to the M1.5 PR (keep / merge / delete + risks).
5. Doubt → fail-closed + escalate to human.

- **No contract-breaking change to `EarnMetrics`** (additive/advisory only).

- **No ADR, no code, no tests, no ledger shard in THIS planning step.**
