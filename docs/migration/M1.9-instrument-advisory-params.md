# M1.9 — instrument **advisory trading-parameters** (config-as-data) (PLAN, docs-only)

<!-- Source: docs/migration/M1.9-instrument-advisory-params.md | Date: 2026-06-18 | Lane: BANXE.RAR → EMI | Server-only (ADR-103) -->

## Status

**PLAN only — no code, no tests, no ADR, no ledger shard in this step.** Next
lowest-blast-radius **advisory** subtrack after M1.8 (asset catalogue), **not greenfield**. It
**extends the existing instrument seam**: the `GET /instruments/{symbol}` endpoint currently
returns a **hardcoded stub** `InstrumentInfo` (a TODO marks "real tick/min/max/fee come from the
catalogue source"). M1.9 replaces that stub with a **deterministic config-as-data advisory
instrument descriptor** (per-symbol trading parameters), reusing the symbol universe. Read-only,
**no live money/orders/balances**. Chosen over KYC/AML (compliance gate, deferred) and over any
live execution/fee-billing path (out-of-scope).

## Why this domain (mapping rationale)

`banxe_to_emi_mapping.md` + deep-read: the instrument descriptor (`InstrumentInfo`) is an
**existing canonical DTO** with a **stubbed** source (ADR-021 catalogue TODO). M1.9 closes that
TODO **advisory-only** with config-as-data — the lowest-blast-radius, non-fund step that
naturally extends the already-migrated symbol/asset seams (M1.8). Trading parameters
(tick/min/max/fee-schedule reference) are **descriptive config**, not balances or live amounts.

## 1. Scope

**Legacy area:** trading instrument/limits configuration — per-symbol tick size, min/max order
quantity, fee-schedule reference. **Descriptive config only** (NOT balances, NOT live order
amounts, NOT positions).

**EMI seam (extend in place):** the existing `InstrumentInfo` DTO + `GET /instruments/{symbol}`
(`api/symbols.py`), today a hardcoded stub. M1.9 introduces a **config-as-data** advisory
instrument-parameters source (e.g. `instruments/params.py`) and feeds the **unchanged**
`InstrumentInfo` from it; the symbol universe is reused from `SymbolInfo`/`MarketDataPort`. The
exact config shape (and whether a `GET /instruments` list is added) is decided in the **M1.9
deep-read (step 0)**. `InstrumentInfo` DTO stays **frozen** (same fields, config-driven values).

## 2. Numeric Invariants (I-01)

- `tick_size` / `min_qty` / `max_qty` are `DecimalString` **trading-parameter config values**
  (price/quantity granularity & order-size limits) — **NOT balances, NOT live order amounts,
  NOT positions, NOT money owned**. They flow through the existing `DecimalStr` discipline — **no
  `BigNumber`, no `float`** outward.
- `fee_schedule_ref` is a **string reference** (which schedule) — **no fee computation here**
  (the `FeeEnginePort` owns fee math; not duplicated).

## 3. Activation Safety

- **Advisory / mock layer ONLY**, config-as-data — describes instrument trading rules; **NO live
  orders, execution, balances, positions, payments, or fund movement.**
- **No live catalogue/exchange calls, no network/keys, no prod wiring** beyond the existing
  endpoint; default sandbox-mock; **fail-closed** (deterministic default/skip when config is
  absent/malformed — never a fabricated live value).

## 4. Duplication Audit (ADR-102) — MANDATORY before any M1.9 code

1. Repo-wide search for instrument/limit/fee-schedule representations — esp. `models.py`
   (`InstrumentInfo`, `SymbolInfo`), `api/symbols.py` (the stub), `ports/market_data_port.py`,
   `ports/fee_engine_port.py` (`FeeEnginePort`), `api/fees.py`.
2. **Canonical instrument SoT = `InstrumentInfo` + the symbols seam** (`SymbolInfo`/`MarketDataPort`;
   real catalogue source = ADR-021 TODO). M1.9 **feeds/extends** it — it must **not** create a
   second instrument model or a second fee SoT.
3. **`FeeEnginePort` = canonical fee-computation SoT** — M1.9 only carries a `fee_schedule_ref`
   string; it does **not** compute or duplicate fees.
4. Source-of-truth + every consumer; keep/merge/delete + risks; doubt → fail-closed + escalate.

### Frozen contracts (must not break)
`SymbolInfo`, `InstrumentInfo`, `MarketDataPort`, `FeeEnginePort`, and the M1.6–M1.8 contracts
(`EarnMetrics`, `AnalyticsContext`, `EarnRatesResponse`, earn statement, accounts metadata,
`CryptoAssetMetadata`/`AssetCatalogResponse`).

## 5. Out-of-scope (strictly NOT in M1.9)

- **All P0 / regulated / live parts:** live orders, execution, balances, positions, payments,
  fund movement, live catalogue/exchange operations.
- **Fee computation / billing** (owned by `FeeEnginePort`); only a reference string is carried.
- **KYC/AML** (compliance gate), cards/banxe-digital, crypto-wallet ops.
- **No user migrations, no DB migrations, no schema changes, no live state machines.**
- **No contract-breaking changes** to `InstrumentInfo`/`SymbolInfo`/`MarketDataPort`/`FeeEnginePort`
  (config-driven values only; same fields).
- **No ADR, no code, no tests, no ledger shard in THIS planning step.**

## 6. Execution outline (for the eventual M1.9 code subtrack — not this PR)
