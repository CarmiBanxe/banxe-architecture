# M1.22 — capability **breakdown** (flatten account capabilities) (PLAN, docs-only)

## Status

**PLAN only — no code, no tests, no ADR, no ledger shard in this step.** The second **list-valued
flattened** breakdown (after M1.21 networks): per-`capability` account counts, derived by flattening
`AccountAdvisoryMetadata.capabilities` over the M1.7 advisory account metadata. Mirrors the M1.21
flatten pattern. Read-only, **no live money/balances/postings/fees** — `capabilities` are
descriptive functional-role labels.

## Deep-read finding — confirmed real list-valued fields (no fabricated field)

`AccountAdvisoryMetadata` (the M1.7 DTO element of `account_metadata().accounts`) has two list
fields: **`capabilities: list[str]`** (mock values `["fiat","crypto","self_custodial"]`, `["fiat"]`,
`["internal"]`) and **`supported_assets: list[str]`**. The module docstring is explicit: *"NO
balances, NO postings, NO amounts, NO money movement; makes NO Midaz LedgerPort"* — so there is no
balance/posting field to leak, and the live ledger is never touched.

**Chosen: `capabilities`** — a small, bounded, descriptive functional-role set (fiat / crypto /
self_custodial / internal), the tightest distinctly-account-domain list dimension. No fabricated
field.

## Domain selection (chosen vs alternatives)

- **Capability breakdown — CHOSEN.** Flatten `capabilities` → per-capability account count; pure
  integer meta from `account_metadata`; descriptive functional roles, far from money.
- **per-supported_asset — DEFERRED alternative.** Real list field, but conceptually overlaps the
  asset-catalogue domain (M1.8/M1.16/M1.21) and is a larger set; revisit later.
- **earn taxonomy↔rates xref — DEFERRED.** Yield-adjacent (re-surfaces `RateCard` APY); awaits
  **explicit operator risk acceptance.**
- **fee-descriptor reference-only / KYC-AML — deferred.**

## 1. Scope

**Legacy area:** none new — M1.22 summarises the existing advisory account metadata by capability.
**EMI seam (derive, flatten):** new read-only endpoint (e.g. `GET /api/v1/catalogue/capability-breakdown`)
returning a new derived DTO (e.g. `CapabilityBreakdown`): a `by_capability` list of
`CapabilityCount` (`capability`, `count`) computed by flattening
`account_metadata().accounts[*].capabilities` and counting accounts per capability, plus
`total_accounts` (number of accounts) and `total_memberships` (sum of counts) and `source`.

**Flatten semantics (documented honestly, per M1.21):** an account with N capabilities contributes
to N buckets; an account with an **empty** capabilities list contributes to **none**. Therefore
`sum(by_capability counts)` = `total_memberships` ≠ `total_accounts` in general (mock accounts have
multiple capabilities, so `total_memberships` > `total_accounts`). Path placed on the catalogue
router alongside the other breakdowns; zero shadow risk (`/catalogue/*` has no `{param}` route). The
frozen `AccountAdvisoryMetadata`, `AccountMetadataResponse` and all breakdown DTOs are **not
modified**; existing endpoints unchanged. The new DTO is a **derived summary**, not a data SoT.
Exact path/shape decided in the M1.22 deep-read (step 0).

## 2. Numeric Invariants (I-01)

- The only numerics are **integer meta counts** (per-capability count, total_accounts,
  total_memberships) — **NOT balances, amounts, positions, ledger postings, prices, APY/yields, or
  computed fees.** `capability`/`source` are strings. No `Decimal`/`BigNumber`/`float` money values;
  **no balance/posting surface, no fee computation.**

## 3. Activation Safety

- **Advisory / mock layer ONLY**, a derived read-only flatten summary — **NO live orders, execution,
  balances, positions, ledger postings, payments, wallet/custody ops, fund movement; NO live Midaz
  `LedgerPort`/`FeeEnginePort` calls; NO infra/secret/PII/ops metrics.**
- No live ledger/exchange calls, no network/keys, no prod wiring beyond an additive public route;
  default sandbox-mock; **fail-closed** — counts derive from the existing fail-closed
  `account_metadata` (malformed config already skipped upstream); never a fabricated capability or
  count; an empty-capabilities account creates no bucket.

## 6. Spec-fidelity note (M1.16 lesson)

`CapabilityCount.capability` (a capability label like `fiat` / `crypto` / `self_custodial` /
`internal`) MUST be specced as a **non-exhaustive `type: string`** with canonical examples in the
description, **never a hard `enum`** — the runtime set grows with the account-metadata config. (Per
the M1.16 CodeRabbit finding; re-applied in M1.17–M1.21.)
