# M1.20 — accounts **breakdown** (by type / ledger-nature / status) (PLAN, docs-only)

## Status

**PLAN only — no code, no tests, no ADR, no ledger shard in this step.** A read-only **accounts
breakdown** deriving per-`account_type` / per-`ledger_nature` / per-`account_status` counts from the
existing M1.7 advisory account-metadata accessor. Mirrors the approved M1.16–M1.19 breakdown
pattern. Read-only, **no live money/balances/ledger postings/fees** — it counts only descriptive
account-metadata categories, never balances.

## Deep-read finding — confirmed real categorical dimensions (no fabricated field)

`AccountAdvisoryMetadata` (the M1.7 advisory DTO element of `account_metadata().accounts`) has
exactly **six** fields: `account_type: str`, `ledger_nature: str`, `account_status: str`,
`supported_assets: list[str]`, `capabilities: list[str]`, `source: str`. Mock values:
`account_type ∈ {INTERNAL, EXTERNAL, SYSTEM}`, `ledger_nature ∈ {ACTIVE, PASSIVE}`,
`account_status ∈ {ACTIVE, …}`. **There are NO balance/amount/posting fields** (M1.7 is
balance-free by design — disclaimer "NO balances, postings, transfers, or live ledger operations").

**Real single-value categorical dimensions for M1.20:** `account_type`, `ledger_nature`,
`account_status` (all `str`). **`supported_assets`/`capabilities` are list-valued** (multi-value,
a different aggregation shape) → **excluded** from this breakdown (could be a future flattened
dimension; not folded in here to keep single-key counting honest). No fabricated field.

## Domain selection (chosen vs alternatives)

- **Accounts breakdown — CHOSEN**, scoped to the **real** `AccountAdvisoryMetadata` single-value
  categoricals (`account_type`, `ledger_nature`, `account_status`). Pure integer meta counts from
  the M1.7 accessor; far from money (counts categories, **never balances/postings**); reuses the
  approved M1.16–M1.19 pattern.
- **earn taxonomy↔rates xref — DEFERRED.** Re-surfaces APY-bearing `RateCard` (yield/money-adjacent);
  awaits **explicit operator risk acceptance**.
- **M1 summary-refresh — NOT now.** Anchor is current to M1.17; a genuinely new advisory domain is
  higher value than a doc refresh — batch the summary refresh after several substeps (rhythm).
- **fee-descriptor reference-only / KYC-AML — deferred.**

## 1. Scope

**Legacy area:** none new — M1.20 summarises the existing advisory account metadata by its real
categorical fields. **EMI seam (derive):** new read-only endpoint (e.g.
`GET /api/v1/catalogue/accounts-breakdown`) returning a new derived DTO (e.g. `AccountsBreakdown`):
`by_account_type`, `by_ledger_nature`, `by_account_status` lists of `AccountDimensionCount`
(`key`, `count`) computed from `account_metadata().accounts` by counting `account_type` /
`ledger_nature` / `account_status`, plus `total` (number of accounts) and `source`. **Path:** placed
on the catalogue router alongside the other breakdowns; `/accounts/metadata` is the only accounts
route (no `{param}`), so a distinct catalogue path has zero shadow risk. The frozen
`AccountAdvisoryMetadata`, `AccountMetadataResponse` and all breakdown DTOs are **not modified**;
existing endpoints unchanged. The new DTO is a **derived summary**, not a data SoT. Exact path/shape
decided in the M1.20 deep-read (step 0).

## 2. Numeric Invariants (I-01)

- The only numerics are **integer meta counts** (per-type, per-nature, per-status, total) — **NOT
  balances, amounts, positions, ledger postings, prices, APY/yields, or computed fees.** `key`/
  `source` are strings. No `Decimal`/`BigNumber`/`float` money values; **no balance/posting surface,
  no fee computation.**

## 3. Activation Safety

- **Advisory / mock layer ONLY**, a derived read-only summary — **NO live orders, execution,
  balances, positions, ledger postings, payments, wallet/custody ops, fund movement; NO live Midaz
  `LedgerPort` calls; NO infra/secret/PII/ops metrics.**
- No live ledger/exchange calls, no network/keys, no prod wiring beyond an additive public route;
  default sandbox-mock; **fail-closed** — counts derive from the existing fail-closed
  `account_metadata` (malformed config already skipped upstream); never a fabricated count or
  category.

## 6. Spec-fidelity note (M1.16 lesson)

`AccountDimensionCount.key` (an `account_type` like `INTERNAL`, a `ledger_nature` like `ACTIVE`, or
an `account_status` like `ACTIVE`) MUST be specced as a **non-exhaustive `type: string`** with
canonical examples in the description, **never a hard `enum`** — the runtime set grows with the
account-metadata config. (Per the M1.16 CodeRabbit finding; re-applied in M1.17/M1.18/M1.19.)
