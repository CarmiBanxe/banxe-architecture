## Status

**PLAN only — no code, no tests, no ADR, no ledger shard in this step.** The third list-valued
flattened breakdown (after M1.21 networks, M1.22 capabilities) and the **last** account-domain
list-flatten dimension: per-`supported_asset` account counts, derived by flattening
`AccountAdvisoryMetadata.supported_assets` over the M1.7 advisory account metadata. Mirrors the
M1.21/M1.22 flatten pattern. Read-only, **no live money/balances/postings/fees** —
`supported_assets` are descriptive asset-support labels, **not balances**.

## Deep-read finding — confirmed real list-valued field (no fabricated field)

`AccountAdvisoryMetadata.supported_assets: list[str]` (via `account_metadata().accounts`) — mock
values: account-1 `[EUR,GBP,USD,CHF,BTC,ETH,USDC]` (7), account-2 `[EUR,GBP,USD,CHF]` (4), account-3
(SYSTEM) `[]` (0, empty). Asset symbols sourced from `_SUPPORTED_FIAT` (EUR/GBP/USD/CHF) +
`_SUPPORTED_CRYPTO` (BTC/ETH/USDC). The module docstring is explicit: *"NO balances, NO postings, NO
amounts, NO money movement"* — there is no balance field; the supported-asset entry is a
descriptive **support label**, not an amount held. No fabricated field.

## 1. Scope

**Legacy area:** none new — M1.23 summarises the existing advisory account metadata by supported
asset. **EMI seam (derive, flatten):** new read-only endpoint (e.g.
`GET /api/v1/catalogue/supported-asset-breakdown`) returning a new derived DTO (e.g.
`SupportedAssetBreakdown`): a `by_supported_asset` list of `SupportedAssetCount` (`asset`, `count`)
computed by flattening `account_metadata().accounts[*].supported_assets` and counting accounts per
asset, plus `total_accounts` (number of accounts) and `total_memberships` (sum of counts) and
`source`. Path placed on the catalogue router alongside the other breakdowns; zero shadow risk
(`/catalogue/*` has no `{param}` route). The frozen `AccountAdvisoryMetadata`,
`AccountMetadataResponse` and all breakdown DTOs are **not modified**; existing endpoints unchanged.

**Account→asset support, not a second asset catalogue:** the asset *keys* overlap the asset
catalogue (M1.8) but the **count semantics are account-domain** (accounts-supporting-each-asset),
distinct from the asset catalogue's own per-asset metadata — **not** a duplicate of the asset
catalogue. The new DTO is a **derived summary**, not a data SoT. Exact path/shape decided in the
M1.23 deep-read (step 0).

## 2. Numeric Invariants (I-01)

- The only numerics are **integer meta counts** (per-asset account count, total_accounts,
  total_memberships) — **NOT balances, amounts, positions, ledger postings, prices, APY/yields, or
  computed fees.** `asset`/`source` are strings (an asset key is a descriptive support label, not an
  amount held). No `Decimal`/`BigNumber`/`float` money values; **no balance/posting surface, no fee
  computation.**

## 3. Activation Safety

- **Advisory / mock layer ONLY**, a derived read-only flatten summary — **NO live orders, execution,
  balances, positions, ledger postings, payments, wallet/custody ops, fund movement; NO live Midaz
  `LedgerPort`/`FeeEnginePort` calls; NO infra/secret/PII/ops metrics.**
- No live ledger/exchange calls, no network/keys, no prod wiring beyond an additive public route;
  default sandbox-mock; **fail-closed** — counts derive from the existing fail-closed
  `account_metadata` (malformed config already skipped upstream); never a fabricated asset or count;
  an empty-supported_assets account creates no bucket.

## 6. Flatten semantics (per M1.21/M1.22)

An account with N supported_assets contributes to N buckets; an account with an **empty**
supported_assets list (e.g. SYSTEM) contributes to **none**. Therefore `total_memberships` (= sum of
by_supported_asset counts) ≠ `total_accounts` in general (mock: account-1 has 7, account-2 has 4,
account-3 has 0 → `total_memberships` = 11 ≠ `total_accounts` = 3). The DTO surfaces both
`total_accounts` (denominator) and `total_memberships`.

## 7. Spec-fidelity note (M1.16 lesson)

`SupportedAssetCount.asset` (an asset symbol like `EUR` / `BTC`) MUST be specced as a **non-exhaustive
`type: string`** with canonical examples in the description, **never a hard `enum`** — the runtime
set grows with the account-metadata config. (Per the M1.16 CodeRabbit finding; re-applied in
M1.17–M1.22.)
