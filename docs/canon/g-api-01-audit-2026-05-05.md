## Executive Summary

**Zero application-level rate-limit middleware exists on any `/auth/*` or `/sca/*`
endpoint** in `banxe-emi-stack`. The FastAPI compliance API exposes six
authentication-surface endpoints with no HTTP-layer throttling. Two partial
protections exist (Keycloak `bruteForceProtected`, SCA in-process attempt counter)
but neither covers the full attack surface. Redis is in the stack; `fastapi-limiter`
is not. No upstream proxy is deployed to provide edge-layer rate limiting.

---

## Finding 1 — No Application-Level Rate-Limit Middleware (CRITICAL)

**Evidence:** Grep across `api/` and `services/auth/`:

```
$ grep -rn "slowapi\|RateLimit\|limiter\|429" banxe-emi-stack/api banxe-emi-stack/services/auth
→ api/routers/auth.py:87:    "too_many_attempts": 429,   ← SCA error code mapping only
→ services/auth/sca_service.py:23: Max 5 failed verifications per challenge → 429
```

No `@limiter.limit()` decorator, no `Depends(RateLimiter())`, no middleware class
registered in `api/main.py` for rate limiting. The only rate-limit-adjacent code is
the `_SCA_ERROR_CODE_TO_HTTP` mapping that translates a service-layer exception to
HTTP 429 — this is not a throttle, it is an error code translation.

**Attack vectors unprotected:**
- Credential-stuffing on `POST /auth/login` — unlimited attempts per IP or account
- Refresh token replay amplification on `POST /auth/refresh`
- SCA challenge creation flood on `POST /auth/sca/initiate`
- OTP brute-force on `POST /auth/sca/verify` (beyond per-challenge in-process counter)

**Regulatory impact:**
- OWASP ASVS 2.2.1: FAILED — no account lockout or rate limit on login
- PSD2 RTS SCA Art.4: PARTIAL — in-process counter on verify only
- GDPR Art.32: WEAKENED — brute-force enumeration of account existence enabled

**Severity:** CRITICAL
**Remediation:** ADR-030 Option (b) — `fastapi-limiter` + Redis

## Finding 2 — Endpoint Inventory: Six Unprotected Auth-Surface Routes

**Evidence:** `api/routers/auth.py` route handlers (grepped `@router.post`, `@router.get`):

| Endpoint | Handler | Current protection | Rate-limit gap |
|----------|---------|-------------------|---------------|
| `POST /auth/login` | `login()` | None | CRITICAL — credential stuffing |
| `POST /auth/refresh` | `refresh_token_endpoint()` | None | HIGH — token replay flood |
| `POST /auth/sca/initiate` | `initiate_sca()` | None | HIGH — challenge flood |
| `POST /auth/sca/verify` | `verify_sca()` | In-process attempt counter (per-challenge) | MEDIUM — counter resets on restart |
| `POST /auth/sca/resend` | `resend_sca()` | None | MEDIUM — SMS/TOTP flood |
| `GET /auth/sca/methods/{id}` | `get_sca_methods()` | None | LOW — DoS via enumeration |

All six endpoints are in a single module: `api/routers/auth.py`.
No `Depends()` for rate limiting on any handler signature.

**Severity:** CRITICAL (login, verify), HIGH (refresh, initiate), MEDIUM (resend), LOW (methods)

## Finding 3 — Existing api_gateway RateLimiter: Not Wired to Auth Surface

**Evidence:** `services/api_gateway/rate_limiter.py`:

```python
class RateLimiter:
    """Token-bucket rate limiter (in-memory stub)."""
    def check_rate_limit(self, key_id: str, policy: RateLimitPolicy) -> bool: ...
```

`services/api_gateway/gateway_agent.py`:
```python
rate_limit = self._rate_limiter.check_rate_limit(api_key.key_id, api_key.tier)
```

This `RateLimiter` is wired to the **developer-facing API gateway** (`/api/gateway/*`)
for per-API-key tier enforcement. It is an in-memory token-bucket (no Redis backend),
operates on `key_id` (API key identifier), and has no connection to `/auth/*` routes.

**Severity:** INFORMATIONAL — existing component, out-of-scope for auth surface
**Note:** The in-memory implementation (`InMemoryRateLimitPolicyStore`) resets on restart;
flagged as a separate risk for the API gateway domain.

## Finding 4 — Keycloak bruteForceProtected: Scope Mismatch

**Evidence:** `infra/keycloak-banxe-emi/realms/banxe-emi-realm.json`:

```json
{
  "bruteForceProtected": true,
  "failureFactor": 10,
  "maxFailureWaitSeconds": 900,
  "waitIncrementSeconds": 60
}
```

KC `bruteForceProtected` with `failureFactor=10` locks a user account after 10
consecutive KC-side authentication failures. This protects the KC token endpoint
(`/realms/banxe-emi/protocol/openid-connect/token`).

**Gap:** The application's `/auth/login`, `/auth/sca/*`, and `/auth/refresh` handlers
in FastAPI are **separate HTTP endpoints** that authenticate via internal services
(`AuthApplicationService`, `ScaApplicationService`). They do not call KC's token
endpoint on every request; brute-force attempts against them do not register with
KC's brute-force detector.

`failureFactor=10` is also permissive compared to PSD2 RTS Art.4 guidance (≤5 SCA
attempts). This should be tightened as a complementary measure.

**Severity:** HIGH — mismatched scope creates a false sense of coverage
**Remediation:** Application-level rate limits (ADR-030) + KC `failureFactor` reduction to 5

## Finding 5 — No Upstream Proxy Rate-Limiting

**Evidence:**

```
$ grep -rn "nginx\|traefik\|envoy\|cloudflare" banxe-emi-stack/infra banxe-emi-stack/docker-compose*.yml
→ infra/penpot/README.md:37: penpot-frontend :9001 (nginx → serves React SPA)
```

nginx is present only in Penpot (separate project, port 9001). No nginx, Traefik,
Envoy, or CDN/WAF is deployed in the path of the banxe-compliance-api (port 8093).
`docker-compose.master.yml` does not define a reverse-proxy service for the compliance
API.

**Consequence:** There is no edge-layer rate-limiting. Application-layer enforcement
(FastAPI middleware) is the **only** available protection for the current evo1 deployment.

**Severity:** MEDIUM — absence of defence-in-depth; application layer must compensate
**Remediation:** Traefik deployment planned for P1 (ADR-030 §Option c); not in scope for P0

## Finding 6 — fastapi-limiter and slowapi Absent from Dependencies

**Evidence:** `requirements.txt`:

```
redis>=5.0.0       ← present
fakeredis>=2.21.0  ← present (test stub)
# fastapi-limiter  ← ABSENT
# slowapi          ← ABSENT
```

Redis is already in the dependency set (used by velocity monitoring, `fakeredis` for
tests). `fastapi-limiter` requires only `redis.asyncio` (subset of `redis>=4.0`).
Adding `fastapi-limiter` requires no new infrastructure.

**Severity:** INFORMATIONAL — dependency gap, easily resolved
**Remediation:** Add `fastapi-limiter>=0.5.3` to `requirements.txt`

**Test coverage gap matrix** (grep `test_auth` and `test_api_sca` for rate-limit assertions):

| Endpoint | Rate-limit test exists | Test file |
|----------|----------------------|-----------|
| `POST /auth/login` | ❌ | — |

| `POST /auth/sca/initiate` | ❌ | — |

| `POST /auth/sca/resend` | ❌ | — |
| `GET /auth/sca/methods/{id}` | ❌ | — |

**Severity:** HIGH (G-API-02) — untested rate-limit claims are no claims at all
**Remediation:** ADR-030 Implementation Plan §5 — `tests/test_auth/test_rate_limits.py`,
≥15 tests with `fakeredis` backend

## Keycloak Config Recommendation (Complementary)

KC `failureFactor=10` is more permissive than PSD2 RTS Art.4 (≤5 SCA attempts).
Recommend reducing to `failureFactor=5` and `waitIncrementSeconds=120` as a
complementary hardening measure alongside ADR-030 application-level limits.
This is a KC-side change (realm export update + KC restart) separate from the ADR-030
implementation.

## Remediation Path

ADR-030 (Proposed, same PR) addresses all findings. Implementation:
1. `fastapi-limiter>=0.5.3` added to `requirements.txt`
2. Redis-backed `FastAPILimiter` initialised in FastAPI lifespan (`api/main.py`)
3. Six endpoints decorated with `Depends(RateLimiter(...))` per Endpoint × Limit Matrix
4. Custom `identifier` callbacks for non-IP key dimensions
5. 429 events emitted to audit trail (ADR-027 `BufferedAuditPort`)
6. ≥15 test cases with `fakeredis` backend

Gap status: **G-API-01 OPEN**, **G-API-02 OPEN**.
Both close on implementation PR merge with evidence (test suite green + 429 audit log entry).
