## Finding 1 — CRITICAL: No FastAPI route for inbound SumSub webhooks

**Gap ID:** G-KYC-03
**Severity:** CRITICAL

`services/webhooks/webhook_router.py` implements `WebhookProvider.SUMSUB` (line 46),
`_verify_sumsub()` (HMAC-SHA1, `x-payload-digest`, lines 104-112), and
`WebhookProcessor._verify_signature()` dispatches to SumSub path (lines 243-245).
The infrastructure to handle SumSub webhooks exists in code.

However, `api/main.py` registers the following webhook routers:
```python
app.include_router(watchman_webhook.router)  # POST /webhooks/watchman
app.include_router(webhook_orchestrator.router)  # POST /webhooks/... (outbound)
```

No `POST /webhooks/sumsub` route is registered. `WebhookProcessor` with SumSub support
is instantiated only in `api/routers/watchman_webhook.py` (with `watchman` secret, not
SumSub). There is no production HTTP endpoint that SumSub can deliver events to.

Consequence: all SumSub applicant events — `applicantReviewed` (KYC pass/fail),
`applicantPending`, `applicantWorkflowCompleted`, `applicantActionPending` (EDD trigger)
— have no delivery target. SumSub would receive connection refused or 404, retry on its
schedule, and eventually stop. The KYC FSM never receives external state transitions.

**Evidence:** `api/main.py` lines 179-186 (router registration block); absence of any
file matching `*sumsub*webhook*.py` or `*webhook*sumsub*.py` in `api/routers/`.

## Finding 2 — CRITICAL: Silent KYC state-machine drift on handler failure

**Gap ID:** G-KYC-03 (fail-mode dimension)
**Severity:** CRITICAL

`WebhookProcessor.process()` (lines 197-215) catches all handler exceptions internally:
```python
except Exception as exc:
    event.status = WebhookStatus.FAILED
    event.error = str(exc)
    logger.error("Webhook handler failed: %s", exc)
```
The exception is NOT re-raised. The route would return whatever HTTP status it is coded
to return (200/202 by default in FastAPI). SumSub receives a 2xx → considers delivery
successful → stops retrying → the KYC decision event is permanently lost.

This failure mode is silent: no Telegram alert, no ClickHouse `KYC_WEBHOOK_FAILED` event,
no DLQ entry. An auditor querying ClickHouse would see `FAILED` status in `webhook_events`
but no downstream evidence that the KYC FSM transition was attempted or retried.

FCA SS21/3 requires KYC systems to produce auditable outcomes. A missed `applicantReviewed`
event leaving a customer in PENDING state indefinitely is a measurable compliance gap.

**Evidence:** `services/webhooks/webhook_router.py` lines 197-215; absence of any
`KYC_WEBHOOK_FAILED` event type in `src/safeguarding/audit_trail.py` or ADR-027 schema.

## Finding 3 — HIGH: No idempotency guard on inbound SumSub processing

**Gap ID:** G-KYC-03 (idempotency dimension)
**Severity:** HIGH

`WebhookProcessor.process()` generates a fresh `webhook_id = str(uuid.uuid4())` for every
invocation (line 154). There is no check against `applicantId + type + createDate` or any
other SumSub-side idempotency key. SumSub retry policy delivers the same event multiple times
(up to 5 retries over ~72 hours with exponential backoff).

Duplicate delivery of `applicantReviewed` (type=GREEN) with no idempotency guard:
- First delivery: KYC FSM transitions PENDING → APPROVED.
- Second delivery (retry): KYC FSM attempts APPROVED → APPROVED (idempotent if FSM guards it)
  OR causes a state log duplication in ClickHouse OR triggers a secondary downstream action
  (e.g., welcome email sent twice, Midaz account provisioned twice).

The `services/webhook_orchestrator/event_publisher.py` DOES implement idempotency (lines 57-73),
but this is for OUTBOUND events only. No equivalent guard exists for inbound SumSub webhooks.

**Evidence:** `webhook_router.py` line 154 (`webhook_id = str(uuid.uuid4())`); absence of
`applicantId`/`createDate`-keyed deduplication in any inbound webhook path.

## Finding 4 — HIGH: DLQ is outbound-only; no inbound SumSub DLQ path

**Gap ID:** G-KYC-03 (DLQ dimension)
**Severity:** HIGH

`services/webhook_orchestrator/dead_letter_queue.py` (`DeadLetterQueue`) operates on
`DeliveryAttempt` from `services/webhook_orchestrator/models.py`. `DeliveryAttempt` is
shaped for outbound delivery: `event_id`, `subscription_id`, `http_status`, `response_body`.
The `delivery_engine.py` exponential backoff schedule (lines 113-118: 1s, 5s, 30s, 300s,
1800s, 7200s — MAX_ATTEMPTS=6) is also wired to outbound delivery only.

No inbound routing path from `WebhookProcessor` to `DeadLetterQueue` exists.
`DLQ.enqueue()` requires a `DeliveryAttempt` object — no adapter exists to map a
`WebhookEvent` (inbound) to a `DeliveryAttempt` (outbound-shaped).

**Evidence:** `dead_letter_queue.py` full file; `delivery_engine.py` lines 29, 88-120;
`models.py` `DeliveryAttempt` dataclass; absence of any `WebhookEvent → DeliveryAttempt`
mapping in the codebase.

## Finding 5 — HIGH: SUMSUB_WEBHOOK_SECRET absent from .env.example

**Gap ID:** G-KYC-03 (secret configuration dimension)
**Severity:** HIGH

`_verify_sumsub()` (lines 104-112) requires `SUMSUB_WEBHOOK_SECRET` to compute the
HMAC-SHA1 expected value. `WebhookProcessor.__init__` accepts `secrets: dict[str, str]`
and falls back to `""` if the key is absent.

`banxe-emi-stack/.env.example` contains no `SUMSUB_WEBHOOK_SECRET` entry. An operator
deploying from the template would have an empty secret, causing every inbound SumSub
webhook to fail signature verification (`_verify_sumsub` returns `False` when `secret`
is falsy — line 110: `if not secret: return False`). All events would be
`SIGNATURE_FAILED` and no KYC FSM transition would occur.

**Evidence:** `.env.example` full grep for `SUMSUB` — zero results; `webhook_router.py`
lines 109-110 (empty secret guard).

## Finding 6 — MEDIUM: No CI test coverage for G-KYC-04 scenarios

**Gap ID:** G-KYC-04
**Severity:** MEDIUM

`GAP-REGISTER.md` lines 326-338 specifies four required test scenarios:
1. Replay attack (same event delivered twice) — assert single FSM transition.
2. Out-of-order delivery (REJECTED after COMPLETED) — assert no state regression.
3. Invalid/missing `x-payload-digest` — assert 401 + audit-log, no FSM transition.
4. Handler error path — assert correct HTTP status returned to SumSub.

A search across `tests/` for `sumsub`, `applicantReviewed`, `replay`, `out_of_order`,
`idempotent` returns zero matches. The existing `tests/test_webhook_router.py` (if present)
covers only the happy-path HMAC verification unit test per GAP-REGISTER description.

**Evidence:** `grep -rn "sumsub\|applicantReviewed\|replay" banxe-emi-stack/tests/` → 0 matches;
GAP-REGISTER.md G-KYC-04 plan (lines 329-335) marks all 4 scenarios as TODO.

## Finding 7 — MEDIUM: n8n not wired for KYC webhook fallback or alert on FSM failure

**Gap ID:** G-KYC-03 (operational alerting dimension)
**Severity:** MEDIUM

The Watchman webhook handler (`api/routers/watchman_webhook.py`) fires an n8n workflow
on list-update events (fire-and-forget pattern). No equivalent n8n workflow exists for
KYC FSM failure alerting. If a SumSub `applicantActionPending` (EDD trigger) fails all
retries, no Telegram alert reaches CTIO or MLRO. The event is silently dead-lettered.

FCA MLR 2017 Reg.28 and EDD obligations require timely action on elevated-risk applicants.
Silent DLQ-to-silence on an EDD trigger violates the intent of the monitoring obligation.

**Evidence:** n8n workflows directory (5 workflows confirmed in ADR-032 audit) — none
reference `applicantActionPending`, `KYC_WEBHOOK_FAILED`, or `EDD_CASE_OPENED` event types.

## Recommendations

- Implement ADR-034 Option (c): `POST /webhooks/sumsub` → 202 OK immediately + Redis queue.
- Add Redis `SETNX` idempotency on `SHA256(applicantId:type:createDate)`, TTL 24h.
- Create background worker consuming Redis queue with exponential retry (×3 for standard, ×5 for EDD).
- On retry exhaustion: `DeadLetterQueue.enqueue()` + Telegram alert to CTIO + MLRO for EDD.
- Add `SUMSUB_WEBHOOK_SECRET` to `.env.example`.
- Add ADR-027 event types: `KYC_WEBHOOK_RECEIVED`, `KYC_FSM_TRIGGERED`, `KYC_WEBHOOK_FAILED`, `EDD_CASE_OPENED`.
- Implement G-KYC-04 test suite: 6 fixtures covering all scenarios in test coverage gap matrix.
