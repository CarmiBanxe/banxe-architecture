# Ledger topology & EMI-conformance notes

- **BIF's code footprint is confined entirely to payment-rail adapter code and does not
  touch D-GL/B-EMI posting paths.** `BifrostAdapter` has no `LedgerPort` import, no
  `post_journal_entry`/`JournalEntry` reference, and its own docstring explicitly states it
  "does NOT call Midaz LedgerPort." Its methods (`submit_payment`, `get_payment_status`,
  `health`, `build_outbound_xml`, `handle_inbound`) operate only on in-memory idempotency
  records, XML descriptors, and ABS/PaymentRailPort status mapping.
- **A redirect decision was made and has since been executed.**
  `MIG-M2.5-BIF-BLOCKER-target-mismatch.md` recommended retargeting the Bifrost adapter to
  `banxe-emi-stack` (option A); `MIG-M2.5-RESCOPE-abs-gap-audit.md` (same day) scheduled
  the Bifrost Wave-D adapter "behind `PaymentRailPort`" as the concrete follow-up; the
  actual `BifrostAdapter` code was subsequently built in exactly that location
  (`services/payment/legacy/`), implementing exactly that port, six days later. This is
  the redirect/RESCOPE precedent the S-A6 plan asked to search for — found, and evidently
  carried through to real code, not left only as a recommendation.
- **Reconciling "BIF = BLOCKER" vs. "M2.1–M2.7 closed":** `MIG-M2.8-acceptance.md` is
  authoritative here, and there is no real contradiction once both items are read
  precisely. Its closed-substep table treats **M2.5 (the ABS reconcile)** as closed
  (IL-388) — a different, already-resolved item. It separately lists **M2.5-BIF (the
  Bifrost Wave-D adapter)** as its own tracked follow-up, explicitly *not* folded into the
  closed-substep table. The original "BIF = BLOCKER" framing was about a scaffold
  target-mismatch (resolved by redirect), not about the ABS reconcile's closure — the two
  MIG threads were never actually in conflict, only easy to conflate by name similarity.
- Minor conformance note: `PaymentRailPort`'s own docstring has not been updated to list
  `BifrostAdapter`/`LegacyAbsPaymentAdapter` among its implementations, even though both
  exist and structurally satisfy the Protocol.

# Gaps & risks (OPEN POINTS)

1. **Verdict wording is stale relative to current evidence.** The chosen verdict phrase
   ("...pending a redirect decision") is the closest of the three fixed options to what
   the evidence shows, but the redirect decision itself is not actually still pending — it
   was made on 2026-06-21 (operator decision A) and has since been executed in code
   (`bifrost_adapter.py`, 2026-06-27). Read the "pending" clause as historical context, not
   as an unresolved item requiring further operator action.
2. **`PaymentRailPort` docstring drift.** The port's own docstring lists only
   `ModulrPaymentAdapter`/`MockPaymentAdapter`/`ClearBankAdapter` as implementations,
   omitting `BifrostAdapter` and `LegacyAbsPaymentAdapter`, which both exist and
   structurally implement it.
3. **BifrostAdapter is sandbox-only by design.** `BIFROST_SANDBOX = True`; no live GCP
   transport is wired. This matches the RESCOPE doc's explicit "advisory/sandbox first...
   operator-gated" instruction, so it is not a defect, but S-A7 must not assume live-rail
   behavior when it reuses this verdict.
